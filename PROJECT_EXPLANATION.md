# Project Overview
This project is an AI-powered Medical Chatbot designed to predict potential medical conditions based on user-provided symptoms. It features a React-based frontend and a Python FastAPI backend. The backend uses machine learning models (Support Vector Classifier and Decision Tree) to analyze symptoms and provide condition predictions, descriptions, and preventive measures. The system includes user authentication (JWT) and data persistence using SQLite.

# Core Components
- **FastAPI Application (`app.py`):** Acts as the central hub linking the HTTP layer, database, and ML models.
- **ML Models (`.joblib`):** The intelligent layer predicting diseases based on binary symptom vectors.
- **React Router (`App.jsx`):** Handles client-side navigation without page reloads.
- **Chatbot Interface (`Chatbot.jsx`):** The main interactive component orchestrating the user's diagnosis flow.

# Important Functions
- `lifespan` in `app.py`: Ensures the heavy ML models are loaded into memory once when the server starts, not per request, ensuring fast API responses.
- `predict` in `app.py`: Transforms string symptoms into a binary array (1 if present, 0 if not) that matches the format the SVC/Decision Tree models were trained on. It computes severity thresholds.
- `handleSubmitSymptoms` in `Chatbot.jsx`: The bridge between the user's selection on the frontend and the AI on the backend.
- `train_models` in `train.py`: Pre-processes messy CSV string data into a clean binary matrix to train the classifiers.

# Architecture
The project follows a standard **Client-Server Architecture** utilizing a **RESTful API**.
1. **Presentation Layer (Frontend):** React SPA (Single Page Application). Manages UI state and user input.
2. **Application Layer (Backend):** FastAPI Python server. Handles business logic, authentication, and orchestrates ML model queries.
3. **Data Layer:** SQLite Database for user data and serialized `.joblib` files for machine learning models.

# Data Flow
1. **Symptom Collection:** User searches or speaks symptoms in `Chatbot.jsx`.
2. **Request Formatting:** React packages symptoms into a JSON array and sends via Axios (POST `/api/predict`).
3. **Backend Processing:** `app.py` receives JSON, validates via `schemas.py`, and maps strings to a binary array mapping.
4. **Model Inference:** The binary array is passed to `ml_model.svc_model.predict()`.
5. **Response Compilation:** Disease name, precautions, and severity are mapped from dictionaries and returned as JSON.
6. **UI Update:** React receives JSON and appends a new bot message block to the chat window.

# API Flow
- `POST /api/auth/register` -> `app.py` -> `db_models.User` -> SQLite (Creates User).
- `POST /api/auth/login` -> `app.py` -> Validates User -> `auth.py` -> Returns JWT.
- `GET /api/symptoms` -> `app.py` -> Returns `list_of_symptoms.pickle` contents.
- `POST /api/predict` -> Intercepted by `auth.verify_token` -> Validates JWT -> `app.py` -> ML Models -> Returns Predictions.
- `POST /api/tts` -> `app.py` -> `pyttsx3` -> Saves `.wav` -> Returns URL.

# Database Flow
The database strictly handles user authentication in this project.
1. Registration creates a record in the `users` table via SQLAlchemy.
2. Login queries the `users` table to match the username/password.
*(Note: Medical data and model weights are NOT stored in the database. They are stored in static CSVs and joblib files).*

# Authentication Flow
1. User submits credentials in `Login.jsx`.
2. Backend verifies and returns a JWT token via `auth.py`.
3. Frontend stores JWT in `localStorage`.
4. `api.js` Axios interceptor attaches `Authorization: Bearer <token>` to all future requests.
5. Protected endpoints (like `/predict`) verify the token using `Depends(auth.verify_token)` before executing.

### 3-minute technical explanation
"The architecture of this project is a decoupled client-server model. 

For the data science portion, I started with medical datasets mapping symptoms to diseases. I wrote a training script using Pandas to clean the data and map categorical symptoms into binary feature vectors. I trained a Support Vector Classifier and a Decision Tree using Scikit-Learn. I serialized these models using Joblib so they can be loaded into the backend without retraining.

The backend is built in Python using FastAPI. To ensure low latency, I used FastAPI's `lifespan` context manager to load the heavy `.joblib` models into memory only once when the server boots, rather than on every request. I implemented an authentication layer using PyJWT and SQLAlchemy with SQLite to secure the prediction endpoints. I also integrated a Text-to-Speech endpoint that offloads the blocking `pyttsx3` generation process into an async thread executor to prevent blocking the main server loop.

The frontend is built with React. I implemented a complex state machine in the Chatbot component to guide users through structured phases: Personal Info, Assessment, Questionnaire, and Results. To make symptom selection accurate, I built an auto-suggest search bar that filters symptoms from the backend, and integrated the browser's native Speech Recognition API to allow hands-free input. Axios interceptors are used to seamlessly attach the JWT token to all API calls. The UI is styled with raw CSS and Lucide React icons to provide a clean, modern medical aesthetic."

### Architecture explanation
"It’s a standard 3-tier architecture. 
1. The **Client tier** is a React Single Page Application (SPA).
2. The **Application tier** is a FastAPI server. It handles routing, JWT-based auth middleware, and orchestrates the AI models.
3. The **Data/Model tier** consists of an SQLite database for structured user data and the file system for static datasets and `.joblib` binary model files. Communication between frontend and backend is strictly RESTful JSON over HTTP."

### Most important technologies and why they are used
- **React:** Chosen for its component-based architecture which makes managing complex UI states (like the multi-stage chat flow) easier.
- **FastAPI:** Chosen for its speed, automatic Swagger UI documentation, and native async support which was useful for handling the blocking TTS library.
- **Scikit-Learn (SVC & Decision Tree):** Chosen because symptom-disease mapping is essentially a high-dimensional multi-class classification problem. SVC performs exceptionally well on high-dimensional sparse data (binary symptom vectors).
- **SQLite:** Chosen for simplicity and zero-configuration persistence, perfect for a scoped project focusing mainly on the AI aspect.

### Most important files and their responsibilities
- **`backend/app.py`:** The core router and controller. It handles model inference in memory and secures endpoints.
- **`backend/ml/train.py`:** The data pipeline script that cleans raw CSVs and outputs the trained model artifacts.
- **`frontend/src/pages/Chatbot.jsx`:** The main user interface that controls the diagnostic workflow and gathers structured symptom data.

### Complete request/data flow
"When a user selects symptoms in the React UI, they are stored in an array. Clicking submit fires an Axios POST request to `/api/predict`, including the JWT token in the header. FastAPI receives the JSON payload, validates the token, and passes the symptom array to a processing loop. The loop initializes an array of zeros representing all possible symptoms, and flips the bits to `1` for the symptoms provided by the user. This binary vector is passed into `ml_model.svc_model.predict()`. The resulting prediction string is used to look up descriptions, severities, and precautions from dictionaries loaded in memory. The backend returns a structured JSON response, which the React app receives and uses to append a new 'Bot' message bubble to the chat UI."

### Potential interviewer questions

**Q: How do you handle cases where the user inputs a symptom not recognized by the model?**
*Based on the code:* "In the frontend `Chatbot.jsx`, symptoms are selected via a filtered dropdown populated directly from the backend's `GET /symptoms` endpoint, preventing invalid symptoms from being submitted. The voice recognition also cross-references transcripts against this list. On the backend, if a symptom string doesn't match the in-memory array mapping, it is simply ignored, though an exception is thrown if the total resulting input vector is entirely zeros."

**Q: Why use both an SVC and a Decision Tree?**
*Based on the code:* "The `app.py` script runs the input against both models and returns both results in the JSON response (`prediction_svc` and `prediction_dt`), though the primary `prediction` and subsequent details (like precautions) rely on the SVC output. This is a common pattern for comparing models or allowing the frontend to show a 'second opinion' to the user."

**Q: How is security handled?**
*Based on the code:* "Security is handled via JWT (JSON Web Tokens). When a user registers and logs in, `auth.py` generates a token. The frontend Axios configuration (`api.js`) has an interceptor that automatically attaches this token as a Bearer token in the headers of all outgoing requests. The `/predict` endpoint uses FastAPI's `Depends(auth.verify_token)` to reject unauthorized requests."

**Q: How do you prevent the Text-to-Speech library from freezing the backend?**
*Based on the code:* "The `pyttsx3` library is synchronous and blocking. In `app.py`, the `/tts` endpoint uses `asyncio.get_event_loop().run_in_executor()` to run the TTS generation in a separate background thread, ensuring the FastAPI server remains responsive to other web requests while the audio file is being generated."
